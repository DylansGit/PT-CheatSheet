Linux Forensics & Incident Response

Linux forensics is mostly about visibility: knowing where the system stores traces of execution, what logs actually matter, and how to pull signal out of an OS that tries hard not to get in your way. This section collects the commands, workflows, and habits you use when a machine starts acting strange, a process doesn't look right, or you need answers fast. Practical triage, artifact hunting, and quick evidence extraction.

1.1 High-Value Directories Where Malware Hides 
/etc/cron.*            
    └─ Cron jobs run automatically. Malware adds tasks to re-execute itself.
    Common abuse:
        - Malicious @reboot jobs
        - Jobs calling hidden scripts in /tmp
        - Jobs running encoded or obfuscated bash

/etc/systemd/system    
    └─ The #1 modern persistence point on Linux.
    Attackers drop:
        - Fake service units (myapp.service)
        - Modified ExecStart= commands
        - Timers that run payloads hourly

/etc/init.d            
    └─ Legacy init scripts (SysV-style). Still honored on many servers.
    Malware inserts:
        - Start-up scripts named like legitimate services
        - Scripts calling remote payloads

/etc/profile.d         
    └─ Automatically sourced for ALL users at login.
    Abused for:
        - Exporting malicious PATH entries
        - Dropping aliases that hide commands (e.g., alias ls="...")

~/.bashrc              
    └─ Loaded for interactive shells. Perfect user-level persistence.
    Indicators:
        - Hidden reverse shells
        - Curl/wget calls
        - base64 decode + eval chains

~/.config/autostart    
    └─ Desktop-based autostarts (GNOME/KDE/XFCE).
    Abuse:
        - .desktop files pointing to hidden binaries
        - Silent startup scripts for RATs/miners

/tmp /var/tmp /dev/shm 
    └─ World-writable + often RAM-backed. Major malware staging locations.
    Typical artifacts:
        - Compiled payloads
        - Droppers
        - tmpfs execution (fileless-like behavior)

/usr/local/bin         
    └─ High-risk for PATH hijacking.
    Abuse:
        - Replacing common commands (ssh, sudo)
        - Typosquatting (sl vs ls)
        - Fake utilities hiding miners

/etc/ssh/              
    └─ SSH configs, host keys, authorized_keys.
    Compromise indicators:
        - Attackers injecting their public key
        - Modified sshd_config allowing weak auth
        - Backdoor binaries replacing sshd

Each directory above represents an automatic execution surface. If an attacker gets one write operation inside these paths, they gain persistence, stealth, and control across reboots and user sessions.

Pro tip: On a live compromise, always diff these directories against a clean baseline or verify integrity using tools mentioned earlier (debsums, rkhunter, auditd).

1.2 Find Recently Modified Files 
sudo find / -mtime -1 -type f 2>/dev/null

What it does: Lists every file modified in the last 24 hours. In incident response, this is one of the fastest ways to identify:

  • Freshly dropped payloads
  • New persistence mechanisms (cron, systemd, bashrc)
  • Tampered binaries under /bin or /usr
  • Log wiping or suspicious log growth
  • Hidden files created by miners or RATs

Common attacker activity revealed by this command:

  • /tmp or /dev/shm payloads compiled seconds before execution
  • Modified sshd_config or added authorized_keys
  • Systemd service files created to maintain persistence
  • Scripts dropped into /etc/profile.d or ~/.bashrc
  • Trojanized versions of system commands (ls, top, ps)

Useful variations:

# Files changed in last 2 hours
sudo find / -type f -mmin -120 2>/dev/null

# Limit to directories most abused by malware
sudo find /etc /usr/local/bin /tmp /dev/shm -mtime -1 -type f

# Track permission or ownership changes
sudo find / -ctime -1 -type f 2>/dev/null

IR tip: Run this immediately on a suspected host to build a timeline. Most malware leaves modification footprints even when trying to be stealthy.

1.3 Find Writable PATH Directories (Privilege Esc) 
find $PATH -type d -perm -002 2>/dev/null

What it does: Searches your $PATH for directories that are world-writable. If attackers can write to a PATH directory, they can insert fake binaries that run instead of real commands.

Why it's dangerous:

  • Attacker creates a fake ssh, sudo, chmod, ls, etc.
  • Because it's in the PATH earlier than the real one, it executes automatically.
  • Used to steal credentials, escalate privileges, or backdoor login attempts.
  • Often paired with cron/systemd to restore itself if deleted.

Common indicators of PATH hijacking:

  • A directory like /usr/local/bin or /home/user/bin with world-writable perms
  • Unexpected binaries with suspicious names (e.g., sl, ps, ssh)
  • Binaries owned by a normal user inside system-level PATH directories
  • Executable scripts referencing /tmp or encoded payloads

Useful follow-ups:

# Show PATH as a list of directories
echo $PATH | tr ':' '\n'

# Inspect contents of the risky dirs
ls -l /usr/local/bin
ls -l /home/*/bin

# Detect files that were recently added
sudo find /usr/local/bin -type f -mtime -1

IR tip: If you find a writable directory in PATH, treat the system as compromised. This is a textbook lateral-movement / persistence foothold used in real intrusions.

2.1 Recursive Search for Suspicious Strings 
grep -RinE "curl|wget|base64|chmod|/tmp|/dev/shm" / 2>/dev/null

Purpose: Hunt through the entire filesystem for indicators of:

  • Downloaders (curl, wget)
  • Encoded payloads (base64, eval chains)
  • Temp-based execution (/tmp, /dev/shm)
  • Permission changes used by malware (chmod +x)

What it reveals in real intrusions:

  • Bash scripts hiding curl-downloaded RATs
  • Miners executed from memory-backed filesystems
  • Injected commands in ~/.bashrc or /etc/profile.d
  • Cron jobs referencing obfuscated payloads

Useful variants:

# Search only /etc (config tampering)
grep -RinE "(curl|wget|bash -c|base64)" /etc 2>/dev/null

# Search for encoded commands 40+ chars long
grep -RinE '[A-Za-z0-9+/]{40,}=' /var 2>/dev/null

# Search for IP addresses (IOC hunting)
grep -RinE '([0-9]{1,3}\.){3}[0-9]{1,3}' / 2>/dev/null

IR tip: If you find curl or wget lines with suspicious URLs or GitHub raw links, you've likely found the initial compromise vector.

2.2 Find Executable Scripts 
find / -type f -perm /111 2>/dev/null

Purpose: Lists every file with the execution bit set - a goldmine when hunting for:

  • Hidden miners
  • Bash/Python reverse shells
  • RAT scripts executing from /tmp
  • Self-extracting droppers

What makes this powerful:

  • Most malware eventually needs execute permissions
  • Attackers often hide payloads as innocently named scripts
  • Even when obfuscated, execution perms expose them

Useful enhancements:

# Filter for scripts (shebang detection)
/usr/bin/find / -perm /111 -exec file {} \; | grep script

# Find recently added executables
find / -type f -perm /111 -mtime -1

# Check only high-risk directories
find /usr/local/bin /tmp /dev/shm -perm /111

IR tip: Focus on executable files that don't belong to legitimate packages or that live outside standard paths. 90% of malicious scripts hide in /tmp, /dev/shm, /var/tmp, or under user homes.

2.3 Find Large or Odd Files 
du -ah / | sort -h | tail

Purpose: Quickly surfaces suspiciously large files that attackers often hide:

  • Memory dumps
  • Exfiltrated data archives
  • Cryptominer logs
  • Botnet configuration caches
  • Huge debug logs created to hide IOCs

Typical findings during IR:

  • 100MB+ archives in /tmp or /var/tmp
  • Gigantic rotated logs covering attacker activity
  • .core dumps from crashed malware
  • Large base64 blob files used as multi-stage loaders

Useful variants:

# Show top 20 largest files
du -ah / | sort -h | tail -20

# Look only in user home dirs
du -ah /home | sort -h | tail

# Only search writable temp locations
du -ah /tmp /var/tmp /dev/shm | sort -h | tail

IR tip: Large unexpected files often mean data staging or payload unpacking. If you see compressed files with long random names - treat them as hostile until proven otherwise.

3.1 Process Filtering 
ps aux | grep -v grep | grep python

Purpose: Quickly identify suspicious processes using pipelines.

Why Python? Python is the most common language for:

  • RATs (reverse shells)
  • Clipboard stealers
  • Crypto miners
  • Credential harvesters
  • Backdoor scripts

Better variants:

# Search for typical reverse shell command patterns
ps aux | grep -E "bash -i|nc -e|/dev/tcp"

# Find processes running from tmpfs
ps aux | grep -E "tmp|dev/shm"

# Catch hidden miners
ps aux | grep -E "python|minerd|cpuminer|xmrig"

IR tip: Combine with lsof -p PID to expose open network sockets, files, deleted payloads, etc.

3.2 Sort Syslogs by Time 
ls -latr /var/log

Purpose: Organize logs by timestamp for quick incident timeline review.

What this exposes:

  • Fresh logs overwritten by attackers
  • Sudden log growth (exfil staging or brute force)
  • Gaps in logs caused by tampering
  • Recently rotated logs hiding attacker activity

Useful variants:

# Only check auth logs
ls -latr /var/log/auth*

# Check systemd journal directory
ls -latr /var/log/journal

# Investigate logs modified in last 24h
find /var/log -mtime -1 -type f

IR tip: Attackers often modify logs during lateral movement. Logs that are far newer or older than expected are red flags.

3.3 Extract IP IOCs 
grep -Eo "([0-9]{1,3}\.){3}[0-9]{1,3}" file.log | sort -u

Purpose: Extract all IP addresses from logs or text files for IOC analysis.

Why it's powerful:

  • Extract attacker IPs from SSH brute-force attempts
  • Reveal C2 callback destinations
  • Pull all network artifacts from system logs
  • Feed directly into threat intel tools

Extended variants:

# Extract IPs + ports
grep -Eo "([0-9]{1,3}\.){3}[0-9]{1,3}:[0-9]+" file.log | sort -u

# Extract URLs (IOC mining)
grep -Eo "(http|https)://[^ ]+" file.log | sort -u

# Extract domain names
grep -Eo "[A-Za-z0-9._%-]\+\.[A-Za-z]{2,}" file.log | sort -u

IR tip: After extracting IPs, enrich them via:

  • VirusTotal
  • AbuseIPDB
  • AlienVault OTX

Grouping repeated IPs often reveals the attacker's infrastructure.

4. Redirection & Logging 
command > out.txt          # overwrite output
command >> out.txt         # append output
command 2> err.txt         # only stderr
command &> all.txt         # stdout + stderr
command >/dev/null 2>&1    # silent mode

Purpose: Understand and leverage shell redirection-critical in forensics, automation, and controlled debugging.

Why it matters in IR:

  • Capture output of suspicious commands without altering system behavior
  • Preserve forensic artifacts in clean text files
  • Prevent noisy tools from spamming stdout/stderr
  • Reproduce attacker behavior safely and document results

Real attack behaviors you can detect:

  • Malware silently redirecting errors to /dev/null to hide failures
  • Scripts appending logs to files in /tmp or /var/tmp
  • Reverse shells that suppress output entirely
  • Installers that redirect everything into a hidden log

Useful IR patterns:

# Collect everything a suspicious binary tries to do
./suspect.bin &> forensic-log.txt

# Capture only errors (common for failed malware attempts)
./payload 2> errors.txt

# Run commands quietly during analysis
some_tool --probe  >/dev/null 2>&1

Advanced tricks:

# Log command output with timestamps
(command; echo "--- $(date)") >> timeline.log

# Capture command + output into a forensic transcript
script -q forensic-session.log

IR tip: Attackers love 2>/dev/null. Any script or cronjob using it should be reviewed immediately-it's a strong indicator of malicious intent or stealth behavior.

5. Practical Bash Scripting Patterns 
# 5.1 Loop through log files
for f in *.log; do
    echo "Scanning $f"
done
# Purpose: batch operations during IR (search logs, extract IOCs, summarize activity)



# 5.2 Hunt for malicious startup/config scripts
for f in $(find /etc -type f); do
    grep -qi "curl\|wget\|bash -c" "$f" && echo "Suspicious: $f"
done
# Usage: finds scripts that download payloads, spawn shells, or modify system configs.



# 5.3 Safe batch rename (snapshot before modification)
for f in *.txt; do
    mv "$f" "${f%.txt}.bak"
done
# Usage: preserve evidence by duplicating originals before analysis.



# 5.4 Auto-extract archives (incident bundles, exfil archives)
for z in *.zip; do
    unzip "$z" -d "${z%.zip}"
done
# Usage: expand attacker toolkits, target logs, or exfiltrated data dumps.

Why these patterns matter in IR:

  • IR often requires touching hundreds of files at once
  • Attackers love scattering IOCs across multiple locations
  • Timelines, hashsets, and IOC extraction all depend on iteration
  • Most Linux compromises revolve around small scripts - looping catches them fast

More powerful IR-ready patterns:

# Extract suspicious commands from every script on the system
for f in $(find / -type f -name "*.sh"); do
    grep -iE "curl|wget|nc -e|bash -i|/dev/tcp" "$f" && echo "[!] $f"
done


# Rebuild a timeline from file modification metadata
for f in $(find / -type f -mtime -2); do
    echo "$(stat -c '%y' "$f")  $f"
done | sort


# Hash all files in a directory tree (malware cluster detection)
for f in $(find /opt/app -type f); do
    sha256sum "$f"
done > hashlist.txt


# Detect obfuscated payloads in scripts
for f in $(find / -type f -name "*.sh"); do
    grep -qiE "[A-Za-z0-9+/]{30,}=" "$f" && echo "[base64 payload] $f"
done


# Report scripts executed recently (mtime-based triage)
for f in $(find / -type f -mmin -120); do
    file "$f" | grep -qi "script" && echo "[recent script] $f"
done

IR pro tips:

  • Never alter suspected malicious files - copy them first.
  • Use loops to isolate time-bound activity (first compromise → persistence → exfil).
  • Batch hashing and scanning lets you quickly map what's “normal” vs attacker-modified.
  • Bash loops outperform GUIs when you're SSH'd into a compromised box at 3 a.m.

These patterns form the backbone of Linux triage workflows used by real IR teams. Mature analysts chain them with grep/awk/sed to create powerful one-liners during live incidents.

6. Live Monitoring Essentials 
sudo dmesg -w
    # Live kernel messages: module loads, hardware events,
    # suspicious driver injection, OOM killer (miners), filesystem errors.

sudo inotifywait -m /etc
    # Real-time watch for changes to configuration files.
    # Detects persistence installation, credential theft,
    # added systemd/cron jobs, modified sshd_config, etc.

tail -f /var/log/syslog
    # Follow system logs for auth events, service crashes,
    # brute-force attempts, privilege escalations, malware activity.

Why live monitoring matters in IR:

  • It lets you catch malware activity as it happens
  • Great for confirming if suspicious processes respawn automatically
  • Useful for watching persistence being installed or triggered
  • Detects real-time network failures or kernel-level abuse

What attackers typically reveal in these streams:

  • Kernel module injections (rootkits)
  • Repeated segfaults from unstable malware binaries
  • Unauthorized service creation (systemd, cron)
  • SSH brute-force login noise
  • Processes crashing and respawning rapidly (miners / bots)

Essential IR expansions:

# Live monitor all auth events (logins, failures, sudo usage)
sudo journalctl -f -u ssh --no-pager

# Watch network activity in real time
sudo tcpdump -n -i any port 80 or port 443

# Monitor directory changes across the system
sudo inotifywait -m -r --exclude ".*\.swp" /

Special IR techniques:

  • dmesg -w shows miners exhausting CPU and triggering OOM
  • inotifywait -m /etc catches stealthy config edits instantly
  • journalctl -f reveals failed logins, privilege escalations
  • tcpdump -w capture.pcap lets you freeze traffic for later analysis

Live monitoring is one of the fastest ways to understand if a compromised system is still “moving,” performing callbacks, or actively being controlled by an attacker.

7. Static Malware Analysis Commands 
file malware.bin
    # Identifies file type: ELF, script, archive, packed binary, compiler info.
    # First step in every malware triage. Detects packers (UPX, MPRESS, custom).

strings -n 6 malware | less
    # Extracts readable strings: URLs, IPs, keys, function names, commands.
    # Great for IOC extraction and spotting C2 infrastructure.

ldd malware
    # Shows dynamic libraries required by the binary.
    # If malware links unusual libs → likely tampering or hidden behavior.
    # Empty output often means static or packed binary.

objdump -d malware | less
    # Disassembles binary to x86/x64 instructions.
    # Perfect for quick inspection without opening full RE tools.
    # Reveals loops, syscalls, encryption routines, suspicious imports.

sha256sum malware
    # Create a strong hash before modifying or analyzing.
    # Used for malware database lookups (VirusTotal / MalwareBazaar).

Why static analysis is essential:

  • Quickly identifies the general malware family (dropper, miner, RAT, botnet)
  • Extracts IOCs without executing the sample
  • Reveals embedded configuration (C2 URLs, API keys, IPs)
  • Shows evidence of packing or obfuscation
  • Lets IR teams classify severity and required containment steps

Common discoveries through static analysis:

  • Suspicious network endpoints embedded in strings
  • Base64/ROT13 encoded payloads inside ELF sections
  • Crypto miner pools (stratum+tcp://...)
  • Hardcoded credentials or SSH keys
  • System commands used for living-off-the-land (bash, curl, wget, perl)
  • UPX-packed malware (file output shows “UPX executable”)

Useful expansions:

# Extract printable strings from specific sections
strings -n 6 -t x malware | grep -iE "http|stratum|ssh|key"

# Identify packers and compression
file malware | grep -i upx

# Dump ELF headers for deeper triage
readelf -a malware | less

# View imported/exported functions (rare but useful)
nm -D malware | less

# Extract embedded files / compressed blobs
binwalk --dd='.*' malware

Detecting malicious behavior without executing the binary:

  • Suspicious imports: system(), execve(), ptrace(), fork(), mmap()
  • Network functions: connect(), socket(), sendto(), recvfrom()
  • File manipulation: open(), read(), write(), chmod()
  • Crypto routines: AES/RC4-like loops, base64 decode loops
  • Persistence clues: references to cron, systemd, ~/.bashrc

Pro IR workflow:

# 1. Hash the file
sha256sum malware > hash.txt

# 2. Identify type + packer
file malware

# 3. Extract strings
strings -n 6 malware | tee strings.txt

# 4. Look for URLs, IPs, indicators
grep -Ei "http|\.onion|\.ru|stratum|ssh|key" strings.txt

# 5. Pull imports/libraries
ldd malware

# 6. Inspect ELF sections for anomalies
readelf -S malware

# 7. Flag suspicious entropy (likely packed)
binwalk malware

IR tip: If ldd returns “not a dynamic executable” and file reports UPX/packed → treat the sample as heavily obfuscated. Avoid execution until unpacked safely in a VM.

Static analysis is how seasoned malware analysts extract 80% of intelligence from a binary before taking the risk of running it in a sandbox.

7.1 Dynamic Analysis (Safe Execution & Observation) 
# Run the sample in a contained environment
strace -f -o trace.log ./malware
    # Logs all syscalls, file access, process creation, network attempts.

ltrace -f -o libs.log ./malware
    # Tracks dynamic library calls, useful for spotting hidden logic.

# Monitor file system writes
inotifywait -m /
    # See which files/directories the binary touches in real time.

# Monitor network behavior
tcpdump -i any -nn -s0 -w capture.pcap
    # Capture all outbound connections for actual inspection.

ss -antp
    # Find new ESTAB connections opened by the process.

# Watch process tree changes
watch -n1 "ps -ef | grep malware"
    # Good for catching child processes, respawns, helpers.

# Show file descriptors of the running process
lsof -p 
    # Great for spotting deleted-on-disk binaries still executing.

# See environment variables loaded on launch
cat /proc//environ | tr '\\0' '\\n'

# Track memory maps
cat /proc//maps | less

# Track live logs the process generates
tail -f /var/log/syslog

# See deleted-but-running binaries
lsof | grep deleted

Why dynamic analysis matters:

  • You observe the program's real behavior rather than guessing
  • You catch filesystem writes, dropped files, and temp artifacts
  • You see network activity and callbacks
  • You map actual syscalls → reveals intent immediately
  • You expose child processes, hidden helpers, and execution chains

Common dynamic indicators:

  • Processes spawning shells or unexpected binaries
  • Creation of new files in /tmp, /var/tmp, /dev/shm
  • Outbound connections to unknown remote IPs
  • Repeated open() calls on system configs
  • Attempted writes to cron/systemd paths

Recommended safe workflow:

# 1. Snapshot the VM
# 2. Record hashes + timestamps
# 3. Run strace + ltrace in parallel
# 4. Capture all outbound traffic
# 5. Watch process tree + filesystem
# 6. Collect all logs and artifacts
# 7. Revert VM the moment you're done

Dynamic analysis completes the picture - it shows what the sample actually does, not what it claims to do.

8. Permissions Mastery 
stat -c "%n %a" *
    # Show filename + octal permissions.
    # Great for spotting insecure files, tampered configs, or overly-permissive scripts.

chmod 600 id_rsa
    # Secure private keys (no group/world access).
    # Attackers LOVE harvesting SSH keys if perms are weak.

chmod -R o-rwx .
    # Strip all 'other' permissions from current directory.
    # Useful for hardening sensitive folders or containing analysis artifacts.

find / -perm -4000 -type f 2>/dev/null
    # List all SUID binaries.
    # SUID = executes as owner (usually root).
    # Critical for detecting privilege escalation opportunities & backdoors.

Why permissions matter in forensics:

  • Misconfigurations often become initial access or privilege escalation
  • Attackers frequently relax permissions to run or persist malicious payloads
  • Weak SSH key permissions leak access to threat actors
  • SUID binaries are one of the most common escalation vectors
  • Malware may alter perms on logs, binaries, or scripts to hide activity

Typical attacker behavior related to file permissions:

  • Setting a malicious script SUID root to gain instant elevation
  • Injecting writable directories into PATH to hijack binaries
  • Making ~/.ssh or authorized_keys world-writable
  • Opening up /tmp or other dirs for arbitrary code execution
  • Changing perms on their payloads to +x (+111) right before execution

Useful IR & hardening commands:

# Show only world-writable files (potential attacker playground)
find / -type f -perm -0002 2>/dev/null

# Show insecure SSH folders
find /home -name ".ssh" -type d -perm -not -700

# Detect unauthorized SUID binaries (compare to baseline)
comm -13 <(sort suid_baseline.txt) <(sort <(find / -perm -4000))

# Show files WITHOUT expected permissions (e.g., config tampering)
find /etc -maxdepth 2 -type f ! -perm 644

SUID deep-dive:

  • Legitimate SUID binaries: passwd, sudo, su, mount, umount, ping
  • Suspicious SUID binaries: anything unfamiliar, located in:
    • /usr/local/bin
    • /opt
    • /tmp or /var/tmp
    • /home//bin
  • Malware sometimes sets its own binary SUID → instant root on execution

Permission recovery patterns:

# Harden .ssh directory
chmod 700 ~/.ssh
chmod 600 ~/.ssh/*

# Reset common system permissions (safely)
chmod 644 /etc/*.conf
chmod 755 /usr/local/bin

IR tip: Any previously unseen SUID binary is a **critical severity** finding. Treat it as a privilege escalation backdoor until proven otherwise.

Permissions form the backbone of Linux security - once an attacker alters them, they can escalate, hide, persist, or destroy evidence.

9. Networking Investigation 
ss -tulpn
    # List all listening ports + owning processes.
    # Reveals rogue services, backdoors, and malware-hosted webservers.

ss -antp | grep ESTAB
    # Show active established TCP connections.
    # Finds reverse shells, C2 callbacks, miners, botnet traffic.

sudo tcpdump -i any -nn -s0 port 443
    # Capture encrypted outgoing traffic.
    # Critical for detecting data exfiltration or TLS-wrapped C2.

What this section exposes during IR:

  • Malware listening on high ports (often 8000–9001, 1337, 5555)
  • Backdoor SSH servers running under random names
  • Unauthorized internal port scanning
  • Reverse shells connecting out to attacker IPs
  • Miners calling out to pool servers
  • Suspicious TLS traffic that shouldn't exist on a server

Deep-dive into each command:

1. ss -tulpn (open ports)

  • Shows PID → lets you link network activity to a binary
  • Detects malware disguising itself as legit daemons
  • Reveals hidden web panels, IRC clients, TCP listeners
  • Attackers often bind Python RATs on random ports

2. ss -antp | grep ESTAB (active connections)

  • Shows outgoing persistence calls (C2 beaconing)
  • Instant way to detect reverse shells
  • Miner pools appear clearly (stratum protocol)
  • Exposes unauthorized outbound SSH

3. tcpdump (packet capture)

  • Identify periodic beaconing intervals
  • Spot large data transfers → exfil attempts
  • Reveal suspicious SNI, TLS client hellos, DNS tunnels

High-value tcpdump variants:

# Capture ALL traffic to file (analyze later in Wireshark)
sudo tcpdump -i any -nn -s0 -w capture.pcap

# Investigate DNS exfiltration
sudo tcpdump -i any -nn -s0 port 53

# Inspect outgoing only
sudo tcpdump -i any -nn -s0 'dst net 0.0.0.0/0'

# Watch connections to a specific IP
sudo tcpdump -i any host 192.168.1.50

Correlate with process activity:

# Match listening ports with running processes
ss -tulpn | awk '{print $5, $7}'   # split port + PID

# Inspect files opened by a suspicious PID
sudo lsof -p 

# Check deleted-but-running malware
sudo lsof -p  | grep deleted

IR tip: If you see an ESTAB connection with a foreign address you don't control, immediately:

  • collect packet capture
  • hash the binary owning the socket
  • block the connection upstream

Network artifacts don't lie - they reveal malware behavior even when binaries are hidden or deleted.

High-value IR use cases:

# Extract attacker IPs from auth logs

11. Analyst Tricks 
for f in /bin/*; do debsums -s "$f" 2>/dev/null; done
    # Integrity check for system binaries (Debian-based).
    # Flags ANY modification to /bin tools (ls, ps, top → common trojan targets).

ps ax | grep -E "bash -i|nc -e|python -c|/dev/tcp/"
    # Detect reverse shells, in-memory payloads, netcat backdoors, Python RATs.

grep -R "[A-Za-z0-9+/]\{30,99\}=" /var/log
    # Extract long base64 blobs hidden inside logs.
    # Often used for staged payloads, obfuscated commands, data exfil.

for u in $(cut -f1 -d: /etc/passwd); do crontab -u "$u" -l 2>/dev/null; done
    # List ALL user cronjobs.
    # Attackers hide persistence under low-priv users.

Why these one-liners matter:

  • They uncover stealthy attacker behavior instantly
  • They work on every compromised Linux server (no tools needed)
  • They reveal persistence, backdoors, and staged payloads
  • They catch “deleted-but-running” malware hiding in memory

Deeper meaning of each trick:

1. debsums check

  • Attackers often trojanize ls, ps, top, ssh
  • This silently detects ANY file mismatch from the original package
  • Must-run if rootkits or stealth tampering is suspected

2. Reverse shell detection

  • Reverse shells leave classic fingerprint patterns
  • “bash -i”, “nc -e”, and “/dev/tcp/” are industry-signature commands
  • Python-based reverse shells are extremely common and easy to hide

3. Base64 detection

  • Attackers hide encoded payloads inside logs to avoid file-based detection
  • Long base64 strings often decode to malware, keys, C2 URLs, commands
  • Spotting them in /var/log is a dead giveaway of tampering

4. Enumerating all cronjobs

  • Persistence often hides under low-privileged users
  • Attackers schedule periodic execution of miners, scripts, and droppers
  • This reveals every cron entry on the box in under a second

Further high-value IR tricks:

# Find deleted-but-running binaries (fileless persistence)
sudo lsof | grep deleted

# Track which processes spawn suspicious children
ps -eo ppid,pid,cmd --sort ppid | grep ssh

# Detect binary injection through LD_PRELOAD
grep -R "LD_PRELOAD" /etc /usr /home

# Detect mass SSH auth failures quickly
grep "Failed password" /var/log/auth.log | awk '{print $11}' | sort -u

# Find scripts executed in the last hour
find / -type f -mmin -60 -exec file {} \; | grep script

IR tip: These little commands often discover more in 30 seconds than an entire SIEM dashboard. They're the “street-smart” toolkit every real SOC/IR analyst keeps in their head.

13. Investigate a Suspicious Machine 
# 1. Look for recent file modifications (2 days)
sudo find / -mtime -2 -type f
    # Reveals newly dropped payloads, modified configs, tampered binaries.

# 2. Check persistence mechanisms
ls /etc/cron.* /etc/systemd/system
    # Cron + systemd = the two most abused persistence layers.

# 3. Inspect active listening services
ss -tulpn
    # Detect backdoors, rogue web servers, unknown daemons.

# 4. Hunt rogue executables
find / -type f -perm /111
    # Finds anything with +x - miners, droppers, scripts, tools.

# 5. Detect encoded payloads (long base64 blobs)
grep -R "[A-Za-z0-9+/]\{40\}==" /
    # Staged payloads, exfil blocks, config blobs.

# 6. Scan for suspicious startup / shell injections
grep -R "curl\|wget" ~/.bashrc /etc/profile.d
    # Catch malicious startup commands pulling payloads.

# 7. Extract strings from suspect binaries
strings -n 8 suspect.bin
    # Extract indicators, URLs, keys, C2 addresses, commands.

High-level incident flow:

  1. Check timeline → find what changed recently
  2. Check persistence → cron, systemd, profile scripts
  3. Check networking → backdoors, callbacks, miners
  4. Check binaries → strange executables, deleted-but-running
  5. Check logs → auth failures, sudo abuse, service crashes
  6. Extract IOCs → strings, URLs, IPs, keys, entropy
  7. Isolate the host if active compromise is suspected

Expanded commands for real IR:

# See deleted-but-running malware
sudo lsof | grep deleted

# View suspicious systemd units
systemctl list-units --type=service | grep -v systemd

# Timeline of /etc modifications
find /etc -type f -printf "%TY-%Tm-%Td %TH:%TM %p\n" | sort

# Review auth activity
grep -Ei "Failed|Accepted|sudo" /var/log/auth.log

# Detect suspicious environment variable injections
grep -R "LD_PRELOAD" /etc /usr /home

What this flow gives you:

  • A fast map of “what changed”
  • Immediate exposure of persistence
  • Clear visibility into active malicious processes
  • Early extraction of IOCs for containment

This is the minimal yet complete IR flow used on compromised Linux hosts: timeline → persistence → processes → networking → logs → artifacts.
